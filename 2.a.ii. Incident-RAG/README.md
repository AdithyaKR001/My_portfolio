# Incident-RAG — grounded incident-resolution assistant

Portfolio Project 2 from the AI/ML transition plan. A production-style **RAG**
service over a large DevOps knowledge base (resolved incidents + runbooks). Ask a
failure question in natural language; it retrieves the most relevant docs, answers
**only from that context**, and **cites the document ids** it used — with an
automated **evaluation pipeline** and a **metrics dashboard** to measure quality.

Runs fully locally on **Ollama** (no API key). Pairs with Project 1 (the agent):
this is the retrieval/grounding layer an agent would call to stop reasoning from
scratch.

## What it demonstrates (portfolio value)

- **End-to-end RAG**: ingest → chunk → embed → vector store (Chroma) → retrieve →
  optional rerank → grounded generation with citations.
- **A real evaluation harness** with RAG-specific metrics (hit-rate@k, recall@k,
  precision@k, MRR, answer key-fact coverage, citation validity) — deterministic
  and unit-tested.
- **A metrics dashboard** (Streamlit) over the eval results.
- **Automated, gated pipeline**: `run_eval` exits non-zero below threshold, so CI
  can block regressions.
- **Loads of data**: ~180 incidents + runbooks generated across 10 failure
  categories, plus ~40 labelled golden Q&A pairs.

## Architecture

```
                          ┌──────────── ingest (offline) ────────────┐
 corpus (JSONL) ─chunk─► embed (Ollama nomic-embed-text) ─► Chroma vector store
                          └──────────────────────────────────────────┘
 question ─► retrieve top-k ─► lexical rerank ─► grounded prompt ─► LLM ─► answer + [citations]
                                                    (Ollama llama3.1)
 golden Q&A ─► run_eval ─► metrics (retrieval + generation) ─► report.json ─► dashboard
```

## The data (generated, not public)

All synthetic and reproducible — generated by `scripts/generate_data.py`:

| File | Contents |
|---|---|
| `data/corpus/incidents.jsonl` | ~180 resolved incidents (symptoms, root cause, resolution) across 10 failure categories and 10 services |
| `data/corpus/runbooks.jsonl` | one runbook per category |
| `data/eval/golden_qa.jsonl` | ~40 questions, each labelled with the relevant doc ids + expected answer facts |

Regenerate or scale it: `python scripts/generate_data.py --incidents 400`.

## Setup (local, Ollama)

```bash
# 1. Ollama + models (chat + embeddings)
ollama pull llama3.1
ollama pull nomic-embed-text

# 2. Project
cd incident-rag
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # defaults to Ollama, no key needed

# 3. Build the index, then use it
python scripts/generate_data.py --incidents 220   # (data is already included; optional)
python -m rag.ingest                              # embeds corpus into Chroma
```

## Use it

```bash
python -m rag.cli                       # ask in the terminal
uvicorn rag.api:app --reload            # REST API at localhost:8000/docs  (POST /query)
streamlit run chat_ui.py                # chat UI with citations + retrieved context
```

## Evaluate + dashboard

```bash
python -m eval.test_eval                # deterministic metric tests (no model)
python -m eval.run_eval                 # full eval -> eval/report.json + report.md
python -m eval.run_eval --retrieval-only  # faster: embeddings only, no LLM
streamlit run dashboard.py              # visualize the report
```

`run_eval` gates on `hit_rate@k ≥ threshold` (default 0.8) and exits non-zero if
below — so it can fail a CI build on a retrieval/quality regression.

## One-command Docker stack

```bash
docker compose up --build
```

Brings up Ollama, pulls both models, builds the Chroma index once (shared volume),
then serves the API (:8000) and chat UI (:8501). First run downloads models (a few
GB). Override the model: `OLLAMA_MODEL=qwen2.5 docker compose up --build`.

## Tuning

Everything is env-driven (see `.env.example`): `TOP_K`, `CHUNK_SIZE`,
`CHUNK_OVERLAP`, `RERANK`. Change one, re-run `python -m eval.run_eval`, and watch
the dashboard — that measure-tune-remeasure loop is the point of the project.

See `EVALUATION.md` for exactly what each metric means and how it's computed.
